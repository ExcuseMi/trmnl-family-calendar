Tracks one line on the map per track

Every track is a line. Which side of the map each one runs on is balanced automatically once you draw the map, busiest track first and evenly split, unless you pin one below. The first track is also who gets any event no rule claims.

Calendars the ICS feeds the events come from

Each calendar needs its ICS link. Pick whose line its events go on; open Rules when one calendar mixes several tracks or you want to rename or hide things.

Rules for every calendar optional

The same rules as inside a calendar, applied to all of them. For example, "anything called Dentist goes on Sam's line". A calendar's own rule wins over one of these.

Runs the real transform.js against your calendars (fetched from this browser), then draws the map exactly as the device would. Feeds that refuse browser requests can be pasted or uploaded instead.

Your configuration paste this into TRMNL

  1. In TRMNL open the plugin's settings and turn Use Demo Data off.
  2. Paste the JSON into Calendars. That box takes either a plain list of ICS links, one per line, or a configuration like this one; it reads whichever it is given.
  3. Set your Location for weather and sunrise/sunset, then save.
Every option, if you would rather write it by hand

The same shape this page produces. tracks and rules are both optional: a bare list of calendars already draws one line per calendar.

{
  "timeZone": "Europe/Brussels",     // optional; the account's zone otherwise
  "locale": "en-GB", "timeFormat": "12h" | "24h" | "auto",
  "tracks": [
    { "name": "Sam",
      "color": "blue",               // hue name, "black", or "gray-10".."gray-75"
      "side": "left" | "right",      // pin the side; balanced by event count otherwise
      "hideIfEmpty": false }         // keep the line on a day it has nothing
  ],
  "rules": [ ... ],                  // applied to every calendar
  "calendars": [
    { "url": "https://.../calendar.ics",   // or webcal://
      "name": "Work",
      "headers": { "Authorization": "..." },
      "includeDescription": false,   // let rules match DESCRIPTION too
      "hideIfEmpty": false,          // keep this calendar's line when empty or unreachable
      "rules": [
        { "match": { "type": "word", "value": "L6" },
          "track": "Bart",           // a name, or a list to share the event
          "rename": false,           // don't rewrite the matched text to the track name
          "rewrite": "", "rewriteFull": false,
          "hide": false,
          "allDay": false,
          "station": true }          // a block the line passes through, not a branch
      ] }
  ]
}
  • Match types: any, all, exact, word, contains, regex, status, weekday, and and/or/not (with matchers).
  • Order: rules are checked in order and the last match wins for each effect. A calendar's own rules beat the top-level ones.
  • Who claims an unrouted event: the calendar's own name, then the first entry in tracks, then the feed's X-WR-CALNAME.
  • Sides are balanced by event count once every calendar has loaded, busiest first, unless a track pins one.
  • Recurring events show if they use RRULE:FREQ=WEEKLY (optionally with BYDAY/UNTIL) or start today.
  • Legacy: people/person are still accepted in place of tracks/track.
