These calendars have not been read

    A calendar link is a password in a URL: anyone holding it can read that calendar. Three ways forward, most private first.

    Lines one line on the map per person

    One line per person. Which side of the map a line runs on, and what colour and dash pattern it gets, are all chosen for you: sides are balanced once the map is drawn, busiest line first and evenly split. The first line is also who gets any event no rule claims.

    Calendars the ICS feeds the events come from

    Each calendar needs its ICS link. Pick whose line its events go on, ctrl-clicking (cmd-clicking on a Mac) for more than one; open Rules when one calendar mixes several lines or you want to rename or hide things.

    Rules for every calendar optional

    The same rules as inside a calendar, applied to all of them. For example, "anything called Dentist goes on Sam's line". A calendar's own rule wins over one of these. Where a rule names a line, ctrl-click (cmd-click on a Mac) to put the event on more than one: that is how a shared event is drawn once, as an interchange.

    Your configuration paste this into TRMNL

    There is nothing to paste yet: add at least one calendar with an ICS link, or go back to the examples and load one.

    1. In TRMNL open the plugin's settings and turn Use Demo Data off.
    2. Paste the JSON into Calendars. That box takes either a plain list of ICS links, one per line, or a configuration like this one; it reads whichever it is given.
    3. Set your Location for weather and sunrise/sunset, then save.
    Every option, if you would rather write it by hand

    The same shape this page produces. lines and rules are both optional: a bare list of calendars already draws one line per calendar.

    {
  "timeFormat": "12h" | "24h" | "auto",
  "lines": [
    { "name": "Sam",
      "hideIfEmpty": false }         // keep the line on a day it has nothing
  ],
  "rules": [ ... ],                  // applied to every calendar
  "calendars": [
    { "url": "https://.../calendar.ics",   // or webcal://
      "name": "Work",                // BECOMES A LINE if any event here goes unrouted
      "headers": { "Authorization": "..." },
      "includeDescription": false,   // let rules match DESCRIPTION too
      "hideIfEmpty": false,          // keep this calendar's line when empty or unreachable
      "rules": [
        { "match": { "type": "word", "value": "L6",
                     "field": "title" },  // or location / description / categories / any
          "line": "Bart",            // a name, or a list to share the event
          "rename": false,           // don't rewrite the matched text to the line name
          "rewrite": "", "rewriteFull": false,
          "hide": false,
          "allDay": false }
      ] }
  ]
}
    • Match types: any, all, exact, word, contains, regex, status, weekday, duration (min/max minutes), time (from/to, "HH:MM", from inclusive and to exclusive), and and/or/not (with matchers).
    • What a matcher reads: a text matcher takes an optional field: title, location, description, categories or any. Left out, it reads the title plus the description, which is what a matcher has always done. Naming description or any switches includeDescription on by itself, so a rule that reads the notes does not also have to remember the switch.
    • Order: rules are checked in order and the last match wins for each effect. A calendar's own rules beat the top-level ones.
    • Who claims an unrouted event: the calendar's own name, then the first entry in lines, then the feed's X-WR-CALNAME. Whichever wins becomes a line: name a calendar after the line it belongs to, or leave it unnamed when its rules route everything, or you get an extra line named after the calendar.
    • Sides, colours and dash patterns are chosen for you: sides are balanced by event count once every calendar has loaded, busiest first, and each side's lines then take solid, dashed, dotted, dash-dot in order. side and color on a line are still read, so a configuration that already sets them keeps working, but there is no longer any reason to write one.
    • Account settings, not config: timeZone and locale are also accepted at the top level and override your TRMNL account's zone and language. Set them only if the account's own values are wrong; the AI prompt above deliberately leaves them out, because an assistant guessing a zone puts the whole day on the board at the wrong hour.
    • Recurring events show if they use RRULE:FREQ=WEEKLY (optionally with BYDAY/UNTIL) or start today.
